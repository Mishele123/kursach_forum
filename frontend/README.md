# Клиентская часть Velo

Веб-интерфейс сообщества велосипедистов на React, TypeScript и Vite. Использует API серверной части из этого репозитория. Сервис `frontend` включён в корневой файл `docker-compose.yaml`.

## Технологии и их назначение

Версии ниже указаны по диапазонам зависимостей в `package.json`. Точные версии установки фиксируются в `package-lock.json`.

| Технология | Версия | Для чего используется |
|---|---|---|
| React и React DOM | 19.3.x | Компоненты интерфейса и отображение приложения в браузере |
| TypeScript | ~7.0.2 | Типы данных API, свойства компонентов и проверка кода при сборке |
| Vite | ^8.3.4 | Сервер разработки, обновление модулей и сборка статических файлов |
| React Router DOM | ^7.18.4 | Переходы между страницами, параметры маршрутов и URL поиска |
| Axios | ^1.20.0 | HTTP-запросы к API, передача cookie и файлов |
| Tailwind CSS | ^3.4.19 | Служебные CSS-классы и общие стили компонентов |
| PostCSS и Autoprefixer | ^8.5.31 / ^10.6.1 | Обработка CSS при сборке |
| Обычный CSS | — | Цвета, сетки, адаптивная вёрстка и оформление отдельных страниц |
| Docker и Nginx | — | Сборка контейнера, раздача интерфейса и проксирование API |
| Python, Playwright и Pillow | `tests/requirements.txt` | Браузерные проверки и работа с тестовыми изображениями |

Приложение работает как SPA: браузер загружает HTML и JavaScript, а последующие переходы между страницами обрабатывает React Router. Данные пользователей, публикаций и велосипедов поступают из backend. Frontend не подключается к PostgreSQL или Redis напрямую.

## Как работает приложение

### Запуск и маршрутизация

1. Браузер открывает `index.html`, который подключает `src/main.tsx`.
2. `main.tsx` создаёт корень React и отображает `App` внутри `StrictMode`.
3. `App` подключает `AuthProvider` и `BrowserRouter`.
4. Router выбирает страницу по адресу. Общая оболочка `MainLayout`
   отображает шапку, навигацию, содержимое через `Outlet` и боковую панель.
5. При смене пути внутри оболочки позиция прокрутки возвращается к началу.

| Адрес | Страница | Доступ |
|---|---|---|
| `/` | Перенаправление на `/feed` | Всем |
| `/login`, `/register` | Вход и регистрация, без общей оболочки | Всем |
| `/feed` | Лента публикаций | Всем |
| `/people` | Поиск участников | Всем |
| `/users/:id` | Публичный профиль участника | Всем |
| `/post/:id` | Публикация и комментарии | Всем; действия зависят от авторизации |
| `/post/create` | Создание публикации | После входа |
| `/profile` | Собственный профиль | После входа |
| `/profile/edit` | Настройки профиля и пароля | После входа |
| `/bikes`, `/bikes/add` | Собственные велосипеды и добавление | После входа |

Неизвестные адреса отображают страницу 404.

### Состояние и авторизация

Общее состояние пользователя хранится в `AuthContext`. При открытии приложения выполняется `GET /auth/me`: успешный ответ заполняет профиль, а при ошибке интерфейс переходит в состояние гостя. После входа или изменения данных профиль можно загрузить повторно через `refreshUser`.

`ProtectedRoute` ждёт завершения проверки авторизации и перенаправляет
гостя на `/login`. Это управление интерфейсом; права на чтение и изменение данных отдельно проверяет backend.

Остальное состояние хранится в компонентах через `useState`: результаты, загрузка, ошибки, поля форм и выбранные фото. Запросы при открытии страницы или изменении параметров запускаются через `useEffect`. Redux, Zustand и отдельная библиотека кеширования серверных данных не используются.

### Путь запроса от интерфейса до API

```text
Действие пользователя
    → страница, компонент или hook
    → services/api.ts (Axios)
    → /api/... → прокси Vite или Nginx → backend
    → JSON-ответ → состояние React → обновление интерфейса
```

Например, лента вызывает `postsApi.getPosts` с `q`, `category`, `limit`
и `cursor`. Прокси преобразует `/api/posts` в `/posts` на backend.
Сервер возвращает `items` и `next_cursor`. При загрузке следующей страницы
новые элементы добавляются к списку с исключением дубликатов.

Условия поиска хранятся в query-параметрах URL; курсор загруженной страницы
хранится локально. При смене условий результаты и курсор сбрасываются.
В текущей версии остаются две известные особенности поиска из шапки:
поле не восстанавливает текст из URL, а отправка запроса сбрасывает категорию.

### Фотографии и стили

Файлы выбираются в `PhotoPicker`, предварительный просмотр создаётся
через временные URL браузера. Загрузка отправляется как `FormData`,
а полученные от сервера пути `/media/...` используются для отображения.
Редактор аватара позволяет настроить обрезку перед сохранением;
галерея открывает изображения в нативном HTML-диалоге.

`styles/tailwind.css` обрабатывается Tailwind через PostCSS.
`index.css` содержит общую тему и адаптивные правила, а CSS рядом
с отдельными страницами и компонентами уточняет их оформление.
Директивы `@tailwind` и `@apply` предназначены для сборщика; встроенный
CSS-анализатор редактора без поддержки Tailwind может предупреждать о них.

## Локальный запуск

Сначала запустите серверную часть по инструкции из корневого README.
Затем выполните из каталога `frontend`:

```powershell
npm ci
npm run dev
```

Откройте http://localhost:5173. По умолчанию запросы `/api` и `/media`
проходят через прокси Vite к http://localhost:8000. При необходимости
задайте `VITE_API_URL=http://localhost:8000` в `frontend/.env`.
Используйте одинаковое имя хоста для интерфейса и API, чтобы работали
cookie сессии. При отдельном размещении интерфейса добавьте его адрес
в список разрешённых источников серверной части.

## Взаимодействие с API

Запросы отправляются с cookie сессии. После входа профиль загружается
отдельно: ответ входа содержит только имя пользователя.
Обновление профиля выполняется через `PATCH /users/me`; интересы
передаются списком. Публичные профили используют отдельные типы данных
без email и сведений о сессии.

Публикации без фотографий создаются через `POST /posts`, с фотографиями —
через `POST /posts/with-photos`. Для добавления фотографий используется
`POST /posts/{id}/photos`. Клиентские проверки файлов помогают пользователю;
окончательная проверка формата, размера и прав доступа выполняется сервером.

## Сборка и проверки

Из каталога `frontend`:

```powershell
npm run build
```

Сборка проверяет TypeScript и создаёт каталог `dist`.
Для браузерных проверок из корня репозитория:

```powershell
.venv/Scripts/python.exe -m pip install -r frontend/tests/requirements.txt
.venv/Scripts/python.exe frontend/tests/verify_comments.py
.venv/Scripts/python.exe frontend/tests/verify_avatar_crop.py
.venv/Scripts/python.exe frontend/tests/verify_profile_design.py
.venv/Scripts/python.exe frontend/tests/verify_garage_design.py
.venv/Scripts/python.exe frontend/tests/verify_profile_posts.py
.venv/Scripts/python.exe frontend/tests/verify_public_profile_design.py
```

Нужны Microsoft Edge и зависимости из файла требований тестов.
Часть проверок использует локальную сборку `dist`, часть обращается
к запущенному интерфейсу на порту 5173. Перед проверками обновите сборку
и запущенный интерфейс. Ответы API подменяются; база данных не изменяется.

Некоторые старые комплексные проверки, включая `verify_main_contract.py`,
`verify_sprint2.py` и `verify_profile.py`, используют селекторы предыдущей
версии интерфейса. Их необходимо обновить перед использованием для приёмки.
Проверки с подменённым API не заменяют интеграционные проверки с сервером.

Скриншоты в `output/`, `tests/artifacts/` и кеш Python не включаются
в Git и контекст сборки Docker.

## Запуск в Docker

Подготовьте корневой `.env` по `.env.example`, затем из корня репозитория:

```powershell
docker compose up -d --build frontend backend
```

Compose запускает необходимые PostgreSQL и Redis, выполняет миграции
перед запуском backend. Интерфейс доступен на http://localhost:5173.
Nginx перенаправляет запросы API и медиа к серверной части.
После изменения исходников пересоберите контейнер интерфейса.
